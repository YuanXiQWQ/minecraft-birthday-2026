# P1：GUI 行为矩阵与无限物品适配审查

日期：2026-10-20。本文提供原版基线、静态证据及候选状态转换，**没有批准临时容器计数、批量策略、结果解锁时机或配方书发现方案**。等级见 [数据核实](vanilla-data.md#1-证据等级)。全部真实客户端操作与浏览器测试为 U，未虚构通过结果。

## 1. 基线与证据定位

- **S1**：AbstractContainerMenu.clicked/doClick、getQuickCraftPlaceCount 等，包含 PICKUP、QUICK_MOVE、SWAP、CLONE、THROW、QUICK_CRAFT、PICKUP_ALL 分支。当前版本枚举名为 ContainerInput，不套用旧教程类名。
- **S2**：AbstractContainerScreen.mouseClicked/mouseDragged/mouseReleased/keyPressed；CreativeModeInventoryScreen.slotClicked。用于区别普通容器与创造目录，不把同一鼠标动作在不同槽位强行统一。
- **S3**：Options 的默认注册与 InputConstants 的常量：E=8、F=9、Q=20、C=6、X=27、数字 1=30、Esc=41；原版鼠标左/中/右=1/2/3。它们是该客户端输入码，**不能直接当作 DOM event.code/key/button**。
- **S4**：AbstractFurnaceMenu.quickMoveStack、Slot.mayPlace、AbstractFurnaceBlockEntity.canPlaceItem/getSlotsForFace。
- **S5**：ResultSlot.onTake 与 CraftingRecipe.defaultCraftingReminder；FurnaceResultSlot 已定位。前者消费输入并处理剩余物，不因使用创造目录就天然变成不消耗。
- **S6**：InventoryMenu、CraftingMenu、Equippable.swapWithEquipmentSlot 的相关路径；完整特殊物品行为仍需复查。
- **D1**：Items 注册/配方/发现进度等，见数据文档。配方书组件路径已定位，完整客户端搜索、滚动、点击和提示行为本轮未逐分支验证（U）。

上述 class 来自校验过的 client.jar，核心条目哈希见 [证据锁](evidence-lock.json)。S 表示检查了有关分支，不表示所有关联类、网络侧和显示侧都已验证，更不代表 C。

## 2. 生存、创造与项目机制

原版生存有有限背包和有限材料。原版创造有无限物品目录，但玩家背包/容器仍是具体 ItemStack；工作台的结果领取和熔炉加工也有自己的消费路径。项目则要求永久解锁后永不丢失、使用/加工不消费，没有额外一套有限普通背包。**简单设置一个 creative=true 并不能满足需求。**

定义审查用记号：U 为永久解锁集合；P 为无限目录；C 为光标；H1…H9 为快捷栏；G 为合成格；F0/F1/F2 为熔炉输入/燃料/输出；R 为结果预览；E 为装备槽；`物品×n` 仅表示临时组。带计数的光标/G/F 仍是候选兼容层，不是已批准产品规则。

## 4. 具体状态转换审查例

这些是书面推演，不是已运行的游戏/浏览器测试。原版列中 S 支持的转移与项目 A 转移分开。

### E01：二值解锁与拆半

初态：U 含木板，P(木板) 永久存在，H1=木板×9，C=空。右键 H1 后按普通槽规则：H1=4、C=5，U 不变（S 基线，A 应用到本项目）。若右键的是 P 而非 H1，则不做“无限的一半”；创造源走 G09 的复制/增减分支。未解锁 P 即使中键/数字键也必须无产物，这是已确定获取门槛。

### E02：分配与复制

C=木板×10，三个空合法格。左拖建议得到各3、C余1；右拖各1、C余7；中拖在创造式允许上下文中按最大组填充。这三者不是同一动作。槽上限来自物品/槽位，奶桶每格最多1。临时 G count 的使用本身仍待 D04 批准，不把例子升级为需求。

### E03：Shift 无限制作

G 是合法木板配方，R=木板×4，材料已永久解锁且制作不减少 G。H 只剩8个木板容量：

- **A-批次填满（推荐候选）**：最多两次完整制作，H增加8；G/U不减。有限上界由接收容量/产物 count 决定，不以材料耗尽为条件。
- **A-单批**：Shift 只领一次4，规则更简单，但偏离原版玩家的批量预期。
- **未批准的危险做法**：重复到 G 材料耗尽；G 永不减，会不终止。

若只剩6个容量，推荐候选按完整批次领4、余2容量保持；是否允许最后一批部分接收并把剩余放到光标/其他出口，需要明确审查，不能以“反正无限”静默丢产物。原版完整溢出/目标选择路径尚需 C，不把该候选说成原版规则。

### E04：蛋糕与三空桶

初态：三个奶桶格各1，其余正确；U 已含空桶（挤奶前置）。原版领取会消费材料并返回三个桶（D/S）。项目须保留奶桶/糖/蛋/麦，不可再直接用桶覆盖奶桶格：

- **A-保留输入＋剩余物记入获取（推荐候选）**：给蛋糕，剩余物已有 U 则不重复通知；若出现新的合法剩余物才加入 U；不生产三个可见有限库存桶。
- **A-保留输入＋独立有界出口**：额外放置三个桶到合法临时目的地，需要容量、GUI、阻塞/回退策略。
- **不推荐**：覆盖奶桶格，使配方消失；或向目录累加三个永久库存单位。

结果“摆出就解锁”还是“领取才解锁”仍待 D05。推荐领取才算取得；合成蛋糕的取得与最终庆典触发分开是已确定需求。

### E05：原木同时是输入和燃料

F0/F1 空，玩家 Shift 原木。原版熔炉 quickMoveStack 先 canSmelt，所以优先入 F0，不因原木也是燃料就优先 F1（S）。高炉中原木无 blasting 配方，仍可按其燃料属性进入 F1（S 推导，完整 C/U）；手动放 F0 则能占槽但不能烧炭。

项目 P→槽建议复制，H→槽建议移动临时组，U 永不减少；不能为了“方便”把所有 Shift 都设计为填任意空槽。

### E06：短燃料与加工

普通 raw_iron 基础200 tick、木棍100 tick。原版消费有限燃料；本项目不消费，候选为保留 F1 引用并在100 tick燃烧周期结束续燃，最终完成一次加工；高炉按对应50/100 tick参数推导。此续燃是 A，不是 D/S 证明原版有无限燃料。

也可把输入/燃料变成无计数配方引用，每次仅产生一个可领取结果，领取后再开启下一轮；这较易控制，但弱化炉连续产出和漏斗行为。两种都须审查；不能自行采用第二种后宣称完整漏斗原版体验。

### E07：漏斗搬运和“无限”

Hopper=木棍×3，目标F1=空。若允许一项普通传输，建议 Hopper变2、F1变1，U(木棍)仍有。传输减少临时源不等于使用消耗；若让每次传输也不减少临时源，则会产生无限复制源，需要额外堵塞与循环规则，不能默认原版漏斗自然解决。

炉输出经漏斗进入另一合法载体，何时永久解锁新产物也是 D05；“成功传到合法目的地算取得”是推荐候选。下游满时无成功转移，不应提前宣布取得。

### E08：盔甲与界面关闭

空胸甲槽右键铁胸甲须装备（确定需求）。原版 Equippable 存在已占用槽交换路径，因此“有装备就永远禁止右键”不是原版事实。具体占用交换/同类无变化/附魔限制与本项目无限手持的处理需复核；不引入无来源的诅咒/属性系统。

关闭 GUI 时光标/个人格清空、已解锁项可重取是 A；另一候选是把临时载体序列化恢复。持久炉输入/结果不应因仅关闭面板而消失。用户应审核退出语义，不能让 UI 卸载暗中决定存档。

## 6. 真实客户端与浏览器核对清单

需要在独立 26.3 客户端环境执行 G01–G30 的适用行，记录模式、屏幕、物品/组件、光标初态、槽位初态、精确输入、结果、视频/截图与版本。重点为创造目录左右键/Shift、中键光标前置、Shift 双击的来源范围、结果槽部分容量、占用盔甲交换、配方书 Shift、炉余热/冷却和关闭行为。

还需浏览器验证右键菜单、中键自动滚动、Pointer Events 取消、数字键/修饰键、输入框焦点、鼠标出界和不同DPR。原版数值不能直接复制进 DOM；如使用标准 DOM button，左/中/右为0/1/2，与本轮 client 常量1/2/3不同。

本轮不启动客户端，不安装测试浏览器或编写浏览器原型。需要后续授权一个明确的客户端验证任务（使用现有合法安装或指定环境，不读取账户凭据）；证据缺口不能被口头“基本与原版一致”替代。
