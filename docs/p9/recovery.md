# 兼容性与发布故障恢复

仅说明恢复步骤，本次不执行历史回退、强推、清档或权限修改。

1. 对照当前远端main SHA、Actions的build/deploy结论、线上`#app[data-build]`及HTML引用的哈希JS。三个状态可能暂时不同；先等待正在运行的发布完成。失败job不得上传/发布新的候选。
2. 只有网络/Actions临时失败且源码仍是期望候选时，可通过已有workflow_dispatch重新运行同一main发布。保持contents:read与部署job的pages:write/id-token:write分离。不要扩大发布目录或仓库权限。
3. 部署成功但资源异常时，记录失败URL、HTTP状态、Content-Type、build和资源清单哈希。普通重新加载/禁缓存加载不会清存档。项目没有Service Worker；不要通过删除localStorage来解决缓存。线上哈希目录与规则/原版清单须与同次构建一致。
4. 发生源码缺陷时，在当前main上以普通新提交修复，运行相应回归和双路径审计后快进推送。若必须恢复旧实现，先审查存档兼容性，再经用户明确授权安排恢复；不使用reset/revert/amend/强推或直接发布未知兼容的旧包。
5. 存档损坏、未知版本、禁用存储或写失败时保留原始SAVE_KEY字节，记录提示。修复存储能力后使用正式Retry；旧标签须Resume到有效代次后才能继续。不要在健康新代次上回写旧快照，不影响同源其他项目的键。
6. 当前内容版本仍p8-experience-2；P9未变更业务存档格式。既有p3—p8迁移由codec测试覆盖，未知/损坏版本不自动删除。计划任何后续格式变更时先增加迁移/失败原字节保护及跨标签测试。

交付源以P9最终提交为准。未来发布失败应保留失败run和用户数据，禁止通过改写历史或清空用户进度制造成功。
