# D06 配方书发现与填充合同

状态：用户已明确答复“批准推荐完整方案”，以下发现及填充合同为当前实施依据。当前授权开发漏斗五槽、有限端口事务和原版配方书；未进入P7网络调度。D04/D05(A)/D07/D08/D09保持。

## 已批准的发现规则

1. 逐条采用已校验Java26.3 `advancement/recipes` 的原始criteria与requirements（外层AND、组内OR），仅作用于P4当前112条可达配方。`inventory_changed`的物品/tag条件映射到永久取得集合，重复搬运临时组不重新触发，也不要求所有材料齐全。原始引用及哈希进入派生数据清单。
2. `recipe_unlocked`引用已发现配方ID。手工成功领取实际配方、或炉输出按D05成功手动/自动取得时，登记实际来源配方ID，再完成原版依赖闭包；看预览、填格、加工完成或看见输出均不触发。特殊修理配方不作为普通书内条目。
3. 原版工作台`tick`初始条件在新书初始化时满足，故新档可查询工作台配方但未取得木板时不可填充；不由主页推进炉加工。初始化不播放历史首次提示。
4. **项目差异一（已批准适配）**：箱子原版要求库存至少10个占用槽。本项目没有普通有限背包，建议将此条件映射为“已永久取得至少10种物品”；不是检查材料齐全或目录翻页。其原始阈值10保留，解释差异明确记录。
5. **项目差异二（已批准适配）**：橡木船原版依赖进入水方块，本项目无玩家移动，不伪造入水事件、不增加游泳系统。该条件保持不满足；仍可手工合成并成功领取橡木船后发现该配方。它不阻断船的可达性，书内不提前伪造发现条件。若用户希望改为取得橡木板即提示，需要另行明确选择该差异；本候选推荐保留原条件边界。
6. “已发现”持久保存配方ID；“当前可填充/制作”按本菜单维度、加工能力、已取得材料身份及原版容量另算；“产物已解锁”只由D05成功取得决定。已发现不授物，未发现也不妨碍手工摆对并领取。
7. 旧存档校验迁移时用已有永久取得事实和初始条件推导发现闭包，不重播历史通知，不猜测旧档曾手工制作过哪个同产物配方。之后成功制作可补齐对应配方ID。新取得导致的新增发现与取得在同一持久事务登记；只有提交者收到一次聚合发现通知，读取/刷新/跨标签投影不重播。书内待查看标记另持久保存，打开对应页/查看条目后标为已看。

## 已批准的填充规则（沿用无限来源与有限组边界）

- 选择满足菜单维度及能力的已发现配方；普通点击按一份输入引用填充，Shift按涉及材料的原版最小槽容量有界填至上限（最多64），不自动领取结果。
- 物品/tag替代只从已永久取得的原版默认身份中选择；优先保留当前格内的兼容默认组，随后采用确定顺序。重复材料可占多个格，不要求目录库存数量。
- 不齐材料只显示屏幕幽灵图案，不写真实槽位、光标或存档，也不参与实际匹配。
- 为避免覆盖既有有限组：只填空格或保留同身份、同组件、布局兼容的已有组；需要挪走异物、含不兼容组件、缩小/重排现有非空输入时整体拒绝，并提示先清空输入。非空光标不参与填充也不被清除；填充提交须满足既有统一载体门禁和队列前置条件。此处不会借清输入悄悄丢弃有限组。
- 炉/高炉只填输入，不自动改燃料或领取实际输出。工作台内容持久，个人四格按D07关闭清空。手动摆格始终可绕过配方书，但不能绕过材料取得门禁。

依据：已提交`data/minecraft/26.3/catalog.json`含1740份recipe advancement；112条可达配方中111条有发现进度，另1条为特殊修理。适用criteria含inventory_changed、recipe_unlocked、1个tick和1个enter_block；其中库存占用条件只有箱子。上述为原始数据证据，不声称已做Java客户端人工操作对照；UI及填充的静态代码证据继续核对。
