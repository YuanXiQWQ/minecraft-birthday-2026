## 2. 浏览器 3D 技术建议

阶段事实：原版模型、GUI、烟花与声音已有局部浏览器证据，完整P2仍需收尾审查；旧的外部隔离仅为历史实验手段，不是当前加载或分发工程规则。

本节保留选型理由；首轮已按授权锁定并测试 Three.js 0.186.1 / WebGL2，Vite 8.3.4 / TypeScript 7.0.2。Babylon/WebGPU/原生后端没有测试。官方功能说明不是项目验收；首轮实际证据及其限制见 P2 报告。

| 候选 | 与项目的契合点 | 取舍及当前建议 |
| --- | --- | --- |
| Three.js + WebGLRenderer | 提供场景对象、透视相机、深度渲染、Raycaster、InstancedMesh；可以作为独立适配器服务二维React GUI | **首选建议，首轮已有局部运行证据**。真实拾取/预览/遮挡/生命周期已测试；原版浏览器视觉与完整目标性能未通过。初测包体/帧间隔见P2报告，不能外推完整场景 |
| Babylon.js的模块化ES包 | 提供较完整场景/材质/拾取/调试能力，可按官方模块/纯导入策略裁剪 | 有力备选。引擎能力较完整，需审查导入/注册及实际产物；不以“引擎大”直接断言最终包更大，也不使用其GUI替代原版二维GUI |
| Three.js WebGPURenderer | 官方提供WebGPU后端及WebGL2回退 | 作为后续证据驱动候选；材质体系/初始化和后端差分增加首轮验证面，不为有限场景默认同时维护两套后端 |
| 直接写WebGL2/WebGPU | 完全控制管线 | 需自行承担场景图、材质、拾取、资源管理等，当前不推荐；不能把低依赖数等同低维护成本 |

官方文档核实（只读，2026-10-20）：[WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)使用WebGL2；[PerspectiveCamera](https://threejs.org/docs/pages/PerspectiveCamera.html)使用透视投影；[Raycaster](https://threejs.org/docs/pages/Raycaster.html)能从相机/NDC发射射线并返回按距离排列的命中及实例索引；[InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html)对相同几何/材质的实例减少绘制调用；[WebGPURenderer说明](https://threejs.org/manual/pages/webgpurenderer)说明WebGPU/WebGL2后端及不同材质体系；[Babylon模块裁剪文档](https://doc.babylonjs.com/setup/frameworkPackages/es6Support/treeShaking/)说明导入和显式注册取舍。

工程推断：首选Three.js/WebGL2是因为本项目需要一个有限渲染层而非完整游戏框架，不是因为已经证明Three.js更快或包更小。React只持有页面/GUI和语义选择，scene3d适配器管理GPU对象及更新，不通过每帧React状态重建全部网格。暂不增加React Three Fiber、物理引擎、ECS或通用世界插件；后续需要时必须有具体证据。

编译后的JS、模型/贴图描述和媒体均可由静态站点按相对URL加载，无需游戏服务器。继续采用双HTML入口、Vite基路径和仅发布dist；原始Minecraft构件不在运行期下载。Three.js/WebGL2方案不支持的设备应提供明确的能力反馈，不悄悄回退为二维游戏。目标设备覆盖和最终支持矩阵尚未验证，不能承诺所有浏览器/GPU可用。

## 3. 原版模型、数据与对象职责

### 3.1 资产路径

建议开发期将Java26.3所需blockstates/models/贴图依赖转换为规范化几何/材质描述，运行时实例化真实三维对象；或预生成等价网格文件后加载。选择哪种中间格式在P2以原版样本验证，不假设通用glTF/JSON加载器天然能读Minecraft格式。

必须验证父模型继承、贴图变量、元素几何、面UV及旋转、方块朝向/状态、原版色调、镂空/透明和动画材质。漏斗不是完整立方体；炉朝向及lit显示需要对应模型/材质状态。特殊模型/方块实体、牛/鸡等实体的几何/姿态来源单列，不能假装所有内容都在一张PNG或普通方块JSON里，也不因此移植完整客户端。

三维资产闭包取“可达物品 + 场景实际引用的自然/装饰/工作站/实体 + GUI/效果”的依赖并集。装饰方块可见不等于允许采集或放置；原版风格、数据版本和许可门槛不变，P1已核实路径/样本不等于3D转换和分发依据已解决。保留[P1资产报告](p1/assets.md)原样，不用本次方向批准替代资源使用依据。

允许预计算网格、共享几何、材质或光照参数；这类三维处理不等于预渲染场景图片。二维物品图标可继续由模型导出，但不能把图标或实际游戏截图当作最终场景方块。

### 3.2 模块和状态边界

| 职责 | 输入/输出 | 不进入其中的内容 |
| --- | --- | --- |
| 场景内容定义 | 稳定sceneId/布局版本、三维静态对象、自然节点、建造区域、允许相机姿态、桌面位置 | 开放世界生成、动态地形扩展 |
| 纯领域模型 | 稳定实例ID、整数逻辑x/y/z、朝向、槽/计时、作物、U；接收命令后产生新状态/事件 | Mesh、材质、GPU句柄、摄像机矩阵 |
| 场景3D适配器 | 内容+当前领域快照→网格/实例映射、可见性、相机、选择/预览 | 直接授予物品或单独保存“另一份世界” |
| 拾取/输入路由 | 画布指针→射线命中对象/单元/面→候选命令；GUI先消费输入 | 仅按屏幕坐标热区推断世界位置 |
| 容器GUI | 稳定工作站ID→屏幕二维槽位及原版操作 | 在世界空间重做一套容器库存 |
| 存档 | 领域状态及内容版本→校验/迁移→重建实例、邻接和场景映射 | 渲染UUID、数组下标、悬浮/预览或半次搬运 |

推荐坐标合同：一方块为一单位，Y向上，X/Z代表水平；使用明确north/south/east/west/down符号与变换表，使模型、单元和漏斗端口一致。模型局部原点/比例、负坐标取整、边界epsilon需在P2固定和测试。具体可建单元集合由各场景配置，未批准任何固定长宽高；P1的70格也不是正式容量上限。

静态环境可共享几何或实例化；可变资源/作物/工作站保留稳定领域ID。InstancedMesh的instanceId只是当前绘制索引，删除/重排后须更新映射，不能作为存档身份。保持相机变换不影响逻辑占用、炉上下左右面或派生连接。

## 4. 三维交互、遮挡与空间保护

建议命令路径：先判屏幕GUI/文本焦点→由画布实际尺寸换算指针→相机射线→真实对象和遮挡→候选单元/方向→三维预览→确认时领域复核→提交状态→渲染投影/保存。预览不修改持久状态，确认时重新校验，拆除/旋转不保留过期命中。

- 不只向“可交互物体”发射射线。不可采集的墙/地形仍有遮挡作用；最近命中是遮挡物时不能继续点后面的炉。材质透明/镂空不自动等于射线穿透，需定义并验证与画面一致的命中规则。
- 预览是带世界变换、能表达深度的三维模型/轮廓，不是鼠标旁二维贴图；合法性/朝向清楚，预览自身不参与下一次目标拾取，也不应通过遮挡错误暗示后方对象可直接操作。
- 点击实际模型/合法表面后选择建造单元；有限区域、占用、必要工作空间/资源和方向都由领域校验。是否需要放置支撑由作者区域与交互合同界定，不引入重力、玩家碰撞或Minecraft全方块物理。
- GUI打开后阻止场景放置/采集/旋转/相机手势透传，关闭/失焦取消未完成指针动作。相机/快捷栏滚轮、右键打开/放置、旋转手势必须通过P2矩阵审查，不能用“能点击”代替原版GUI验证。
- 第一人称眼位通过构图/建造区保证可操作；不足时评审受限视线调整与作者布局。任何候选保持场景内部眼高感，不把俯视/自由飞行控制器装进产品。具体手势、视线范围和是否允许切换观察点尚未批准；原文旋转/缩放仅为待评估候选，不能据此改变第一人称产品要求。自由鼠标射线与无准星已确定，不强制 Pointer Lock。
- 防软锁同时考虑能力来源与视角下的交互可达性。必要铁/替代燃料/工作站/耕地/桌面在允许视角下不能永久不可选；视觉被挡不等同规则已消耗，也不能靠穿墙点击掩盖。验证假设布局后的最后来源、联合工作台/炉空间和补货占用，参考P1算法但不以手工小图替代P4/P7完整证明。

多漏斗的规则沿用可审查的端口、有限载体移动、冷却/顺序和派生邻接方向；相邻关系只由sceneId/逻辑坐标/方向得出，不由三维模型外观相碰或摄像机投影得出。多个实例/连接/循环不需要世界物理、红石或玩家实体。P1的固定8tick和候选取得/临时计数仅是实验条件，原版协调与正式适配仍待核实。

### 测量协议建议

1. P2开始前登记CPU/GPU、操作系统、浏览器版本、是否硬件加速、可取得的后端/驱动信息、视口/画布/DPR、固定相机、模型/纹理/实例/粒子数量及资源哈希。不读取账户或无关设备信息。
2. 固定同一场景与操作序列，分别测冷加载、暖态空闲、连续拾取/放置、密集合法布局、打开GUI、粒子/音频及联合负载。负载档位是测试配置，不能变成产品7×5×2或物品/功能削减要求。
3. 建议暖态30秒后采样60秒并重复至少3次，输出原始帧间隔、p50/p95/最大帧时间、FPS、主线程拾取/预览响应、draw calls/三角形/纹理与几何数量、加载/解码时间、构建及传输字节。GPU计时仅能力允许时采集并标明来源；对象/纹理数量不冒充准确显存字节，帧间隔也不等于纯GPU耗时。
4. 同时记录场景多次进入退出后的资源数量/内存趋势、上下文丢失/重建、错误请求、异常和状态保留。自动测试侧重正确性，目标设备人工实测提供性能证据；截图不能单独证明帧率、三维命中或音频通过。
5. 60fps是原架构建议目标，尚无设备实测或正式预算；依据数据审查并冻结允许实例/几何/粒子负载、DPR和性能门槛。若预算尚未确定，采样完成也不能宣称P2性能验收通过。不能把生成代码行数或测试耗时换算开发工时。

推荐优化顺序是有限场景资产/几何裁剪、共享几何/材质与实例化、按需更新/受控DPR、资源释放与合理缓存，再评估照明/阴影成本；保留原版模型视觉、三维遮挡和全部明确功能。不能以性能为由退回2D/A或改成通用烟花。默认静态环境加有限光照只是首轮建议，原版材质/光照观感必须对照，不能声称照搬Three.js默认材质即原版一致。
